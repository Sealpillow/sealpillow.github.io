A test runner for 25 storefronts

Before every release, someone had to click through sign-in, the bag, checkout, payments and the account pages on each storefront, market by market, and write down what they saw.

So, as a personal project, I built a test runner that does that walk instead. It opens a browser per market, follows the shopper's path step by step, screenshots every step, and turns the run into a sign-off report.

    The UAT journey

    One shopper, start to finish

    For release testing, one browser per market walks the whole path in order, so the bag and the sign-in carry over just as they do for a real customer. A failed step is recorded with its screenshot and the journey carries on.

    What a run leaves behind

    Evidence people can sign off on

    The UAT report

    One page, made from any saved run, that prints to PDF for sign-off.

    • Every test against every market: passed, failed or skipped, with why
    • Failures grouped by problem, so one site issue across five markets reads as one row
    • Flags a failure that also failed in earlier runs as likely a known issue
    • Manual checks for what automation can't see, and Tested by / Approved by lines

    Staging vs Live

    Run the same tests on both sites, press Compare, and get one report of what differs, saved as a PDF with every screenshot inside.

    • Steps that differ between the two sites come first
    • Steps failing on both usually point to the site's code, not its setup
    • On Live the journey runs only read-only steps: no orders, sign-ins or forms

    Under the hood

    Built to keep going

    Staging sites are slow and flaky, so most of the work went into making a run finish and say clearly what happened.

    Recovers from a stuck page

    When a page stops responding, the journey closes that tab and carries on in a fresh one, still signed in with the same bag, so one hang doesn't fail every step after it.

    Runs in parallel

    Each test gets its own browser. With separate test accounts, the desktop and phone journeys run side by side, so a UAT run takes about as long as one journey.

    Says what it expected

    Every step records what it should see and what it got, with a screenshot. A timeout says how long it waited and for what.

    Explains slow runs

    A wait log per journey shows how long each step took and where the time went: page loads, waiting for elements, clicks.

    Configured, not coded

    Markets, products, promo codes, campaign content and payment methods live in settings, edited in the UI, so a new campaign needs no code change.

    Explains itself

    Each test has an info card: what it checks, what it does to the site, the settings it uses, when it fails, and its last result.

    How it grew

    From a desktop window to a browser app

    The first version answered "does checkout still work?". As more of the team leaned on it, it needed history, reports and a way to set it up without editing files.
